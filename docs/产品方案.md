# 一、项目概述
## 1.1 产品名称
AI求职信息智能筛选助手
## 1.2 产品定位
面向应届秋招学生的**本地轻量化、只读式、低风险**求职信息自动化采集与智能筛选工具。用户可自定义选择1个或多个QQ求职群进行监听；自动抓取群内文本、图片、网页链接，对图片执行OCR、对链接拉取网页正文；基于**用户自行粘贴录入的简历与求职意向**，完成信息抽取、岗位匹配打分、本地归档、日报汇总。全程本地单机运行，**不会主动发送任何QQ消息**，最大限度降低QQ账号风控风险。

## 1.3 核心设计原则
1. **只读优先，风控第一**：仅监听读取消息，禁用所有消息发送接口；单机本地部署，禁止云服务器挂机。
2. **配置驱动，无硬编码**：监听群列表、个人简历、求职偏好全部由用户配置，程序不内置固定用户画像、固定岗位偏好。
3. **多模态信息捕获**：支持文本、图片OCR解析、网页链接正文抓取，完整捕获宣讲海报、招聘网页内的岗位信息。
4. **数据本地留存**：原始消息、OCR识别结果、网页抓取内容、解析后的岗位数据全部保存在本机，不上传第三方服务器。

## 1.4 项目价值
1. **个人效率价值**：替代人工刷群、保存海报、逐个点开链接抄录岗位信息，减少秋招信息整理耗时。
2. **信息完整价值**：解决招聘信息分散在文字、图片海报、外部网页的痛点，避免遗漏关键岗位条件。
3. **工程实践价值**：覆盖客户端协议消息监听 + 多模态处理（OCR+网页爬取） + LLM语义结构化解析 + 本地持久化存储，项目内容可直接用于简历、面试口述。

# 二、需求分析
## 2.1 用户痛点
1. 求职群消息量大，闲聊、广告混杂宣讲招聘信息，人工筛选耗时，容易漏掉优质岗位。
2. 求职群动态变化，需要随时增减要监听的群，不能写死固定群ID。
3. 招聘信息载体多样：部分岗位写在文本，部分是图片海报，部分需要打开外部网页查看详情，人工处理繁琐。
4. 每个人简历背景、求职意向不同，筛选规则不能写死，需要支持用户输入自己简历和求职偏好来做岗位匹配。
5. 大量零散岗位信息无法自动归档，难以统一对比、复盘投递机会。

## 2.2 功能需求
1. **监听群配置管理**
    - 用户配置QQ群ID列表，支持1个或N个群；仅监听列表内群，不在列表中的群消息直接丢弃，不进入后续处理流程。
    - 通过配置文件修改群列表，修改后重启程序生效（V1.0暂不支持热加载）。
2. **多模态消息采集**
    - 采集群内普通文本消息。
    - 识别消息内网页URL，自动拉取网页正文。可配置开关，随时启用/关闭网页抓取。
    - 捕获消息内图片，本地下载图片并调用本地OCR提取图片文字。
    - 约束：程序只读取资源，不会发送任何消息、图片、回复。
3. **用户简历&求职意向配置**
    - 用户粘贴完整简历文本。
    - 用户填写求职意向：目标岗位、意向城市、可接受行业、硬性排除项。
    - 系统读取用户输入内容作为岗位打分依据，程序内部不预置任何用户标签。
4. **AI智能信息解析**
    - 消息分类：区分宣讲通知、正式招聘、内推信息、闲聊广告、诈骗信息。
    - 结构化提取字段：公司名称、岗位名称、工作地点、学历要求、技术栈要求、投递渠道、截止时间、信息来源。
5. **岗位匹配打分**
    - 将结构化岗位信息，和用户简历+求职意向一并送入大模型。
    - 输出0~100匹配分数+简短打分理由。
6. **岗位推荐阈值过滤**
    - 配置文件可配置推荐分数阈值（默认 80 分，当前实例配置 50）。所有岗位无论分数高低，结构化 数据全部持久化保存到底层 jobs 目录；**仅分数大于等于阈值的岗位，才会在控制台推荐输出、Markdown 日报中展示**。低于阈值的岗位仅写入后台存档，控制台只打印极简日志，不输出完整岗位信息，不加入日报推荐列表。
    - **阈值修改全量重算（v0.7.0）**：修改 `recommend_score_threshold` 后（Web 配置页保存或程序重启），自动将全部已存档岗位按新阈值重新比对推荐标记（`recommended = score >= threshold`，只改标记不改分数），保证"改一次阈值即全量重新筛选"，实测扫描=36 更新=0 阈值=50。
7. **自动去重归档（v0.7.0 增强）**
    - 基于**归一化**公司名称+岗位名称做岗位去重：公司别名归一化表（华为半导体业务部/华为海思→华为，普渡科技/普渡机器人→普渡）+ 去公司后缀/集团/股份冗余；岗位名去 J 编号/括号/【信息未提及】噪音；泛校招（软件开发工程师/校招/秋招等）同公司只保留一条。
    - **启动自动去重**：主程序启动时自动清理重复岗位（保留最优：推荐优先 → 分数高 → 字段完整 → 文件新），重复文件移入 `data/jobs_dedup_backup_<时间戳>/` 备份**不删除**；缺公司名/损坏文件不参与去重，不丢任何岗位信息；实测华为系/普渡多条合并，43→36。
    - 原始消息、OCR文本、网页正文、结构化岗位数据本地分目录存储。
8. **每日汇总日报**
    - 自动汇总当日新增岗位，按匹配分数降序排序，输出Markdown格式日报。
9. **启停控制**
    - 支持手动开启/关闭监听，间歇运行，规避长时间挂机带来的账号风险。
10. **残缺岗位自动补全（v0.7.0）**
    - 缺公司名/岗位名的残缺岗位，在打分前自动联网补全：DeepSeek 生成检索词 → 多源搜索（Bing/神马/百度，全部检索词都执行）→ HTTP 抓详情页 → **失败降级 Playwright 无头浏览器渲染**（官网校招入口挖掘 + zhiye 校招页抽取）→ LLM 抽取完整字段（不编造，缺失保持【信息未提及】）。
    - 实测：普渡机器人自动补出"后端开发工程师"、纵维立方自动补出"深圳/本科硕士博士"。
11. **员工风评/WLB 检索（v0.7.0）**
    - 打分前自动检索公司外部资料（员工风评/WLB/舆情）：多路检索词 + 多源搜索 + 牛客页面 HTTP 抓取；搜索引擎不索引牛客内容时**自动浏览器渲染牛客搜索页**兜底（面经/员工评价/offer 投票，同公司缓存只查一次，上限 200 条）。
    - 实测普渡命中多篇真实牛客面经并入打分提示词；**小红书确认登录墙**（无头浏览器被"手机号登录"拦截，属平台限制，保留语境检索词尽力命中摘要）。
12. **Web 手动录入 / 删除岗位（v0.7.0）**
    - Web 面板「＋ 手动录入」：公司/岗位必填 + 扩展字段，走与群消息完全一致的分组打分/去重/落盘链路（LLM 不可用时降级未打分记录，不丢录入）。
    - Web 面板每行「删除」按钮：投完的岗位一键移除，**删除 = 移入 `data/jobs_deleted_backup_<时间戳>/` 备份可恢复**；文件名 basename 白名单 + `.json` 后缀校验防路径穿越。

## 2.3 非功能需求
1. **账号安全**：NapCat设置纯只读模式，关闭所有发送接口；仅本地单机运行，禁止云服务器部署。
2. **稳定性**：网页抓取增加超时、最大页面大小限制（`web_max_bytes` 已上调 4MB，公众号长文可抓取），防止程序卡死；OCR占用资源可控；抓取失败时标记异常，不阻断整体流程；残缺补全链路支持 Playwright 无头浏览器渲染兜底（HTTP 抓不到的 JS 渲染页），渲染失败同样降级不阻断。
3. **可配置性**：监听群、简历文本、求职意向、网页抓取开关、OCR开关全部放在配置文件，无需修改代码。
4. **数据隔离**：原始消息、图片、OCR结果、网页内容、岗位JSON、日报分开目录存放；去重/删除的岗位单独归档备份目录（`jobs_dedup_backup_*` / `jobs_deleted_backup_*`），运行日志统一 `data/logs/`。

# 三、整体架构设计
三层架构：**NapCat消息采集层 → 多模态处理层 → AI解析&打分&存储层**

## 3.1 NapCat消息采集层
- 能力：本地监听QQ消息，根据配置的群ID列表过滤消息；不在列表内群消息直接丢弃。
- 输出：消息元数据（群ID、发送时间）+ 消息内容（文本、图片资源地址、URL链接）。
- 事件兼容（v0.7.0）：同时放行 `post_type="message"` 与 `"message_sent"` 两类事件——NapCat 对登录 QQ 自己发送的群消息/群内历史同步消息标记为 `message_sent`，仅放行 `message` 会导致该群 0 条消息进入链路（实测某群全量 `message_sent`）；历史补拉 `history_to_message` 同步受益。
- 安全配置：禁用所有send发送接口，关闭自动回复，纯消息接收。

## 3.2 多模态处理层（新增模块）
接收NapCat推送消息，分3条分支处理：
1. 文本：直接透传给下游模块。
2. 图片：本地下载图片 → 本地OCR识别文字 → OCR结果附加到消息文本。
3. URL链接：正则提取链接 → HTTP请求拉取网页 → HTML清洗提取正文 → 正文附加到消息文本。
> 控制策略：网页抓取支持开关；设置超时，限制页面大小（`web_max_bytes=4MB`，公众号长文可抓取）；普通流程不处理需要登录、JS强渲染页面（残缺补全链路例外：支持 Playwright 无头浏览器渲染兜底）。

## 3.3 AI解析&打分&存储层
1. 输入：合并后的完整文本（原始消息+OCR文字+网页正文）。
2. 消息分类：判断消息是否为有效招聘信息，过滤闲聊广告。
3. 结构化抽取：提取岗位标准化字段。
4. **残缺补全（v0.7.0）**：缺公司名/岗位名的岗位先走浏览器补全链路（检索 → 抓取/渲染 → LLM 抽取），补全成功就地更新，失败保持残缺不编造。
5. 岗位匹配打分：传入【岗位信息 + 用户简历 + 用户求职意向 + 公司外部检索资料】，LLM 输出匹配分数和理由；读取配置 `recommend_score_threshold`（默认 80，当前实例 50）：**分数 ≥ 阈值** 标记为推荐岗位（控制台输出完整信息、写入日报），**分数 < 阈值** 标记为仅存档岗位（仅 JSON 存档、控制台极简日志）。
6. **风评检索（v0.7.0）**：打分前自动检索公司员工风评/WLB（多源搜索 + 牛客浏览器兜底 + 缓存），并入打分提示词；检索失败自动降级（"未自动联网核验，WLB 需人工自查"）。
7. **去重与阈值重算（v0.7.0）**：主程序启动时自动执行——岗位自动去重（归一化键分组保留最优，重复移入备份）+ 推荐标记全量重算（按最新阈值比对全部岗位）。
8. 持久化存储：保存原始素材与结构化岗位JSON。
9. 日报生成：定时读取本地岗位数据，生成Markdown日报。

## 3.4 完整运行流程
1. 用户提前编辑配置文件：填写监听群ID列表、粘贴简历文本、填写求职意向，开启/关闭OCR和网页抓取。
2. 本地启动NapCat（只读模式）；在 DeepSeek 开放平台创建 API Key 并填入配置文件（官方 API 直连，无中间网关）。
3. 启动主程序（`tools/scripts/start_all.ps1` 一并启动 Web 控制台；日志输出 `data/logs/`）：先自动执行**岗位去重**（重复移入备份）与**推荐标记全量重算**（按当前阈值）。
4. NapCat捕获QQ消息（兼容 `message` / `message_sent` 两类事件），校验群ID是否在监听列表；不在列表直接丢弃。
5. 列表内消息送入多模态处理模块，处理图片OCR、网页抓取（4MB 上限）。
6. 合并全部信息文本，送入大模型。
7. LLM判断是否招聘信息；有效则抽取结构化岗位信息。
8. 残缺岗位（缺公司名/岗位名）先走**浏览器自动补全**（检索 → 抓取/渲染 → LLM 抽取）。
9. 打分前自动**检索公司风评/WLB**（多源 + 牛客浏览器兜底），并入打分提示词。
10. LLM对比岗位与用户简历意向（含公司外部检索资料），输出匹配分+理由。
11. 读取配置的推荐分数阈值（当前 50），判断岗位是否为推荐岗位：
- ≥阈值：标记推荐，控制台打印完整岗位信息；
- ＜阈值：仅后台存档，控制台仅打印一行极简日志。
12. 结构化岗位数据写入本地 JSON（去重归一化）；推荐岗位汇总写入 Markdown 日报。
13. Web 面板可查看岗位看板、手动录入新岗位、手动删除已投完岗位（删除移入备份可恢复）。
14. 用户手动关闭程序，停止监听（`tools/scripts/stop_all.ps1`）。

# 四、详细功能模块设计
## 4.1 群监听配置模块
配置项：`monitor_group_ids = [123456,789012]`，数组类型，支持1个或多个群ID；空数组不监听任何群。
逻辑：NapCat收到消息优先判断群ID，不匹配直接丢弃，不进入下游流程；事件类型兼容 `message` / `message_sent`（v0.7.0，NapCat 自发送/群内同步消息标记为 `message_sent`）。
V1.0实现：修改配置文件后需要重启程序加载新配置。
**历史消息补拉（v0.6.4）**：NapCat 正向 WebSocket 只推送实时事件、不补历史，电脑休眠 / 程序重启期间群消息会整体错过；连接成功（含断线自动重连）后通过 NapCat HTTP 扩展接口 `get_group_msg_history` 低频补拉最近 `backfill_count` 条（默认 50），按 `(群号, 消息ID)` 与 `raw_msg` 落盘文件名去重，逐条复用实时消息链路（多模态 → AI 解析 → 打分 → 归档）。安全约束：仅拉取历史消息、不发送任何内容；每次连接只补拉一次、条数上限可配；单群失败 WARN 不阻断、单条处理失败隔离不中断。配置：`napcat.history_backfill`（默认 true）/ `backfill_count`（默认 50）/ `backfill_http_url`（默认 `http://127.0.0.1:3002`）。

## 4.2 多模态消息解析模块
1. 文本分支：直接透传。
2. 图片分支：本地下载图片，调用PaddleOCR识别；识别结果附加到消息文本；识别失败标记OCR异常。
3. URL分支：正则提取http/https链接；HTTP GET请求，清洗HTML标签提取正文；设置超时、页面大小上限；支持开关`enable_web_fetch`。

## 4.3 用户简历&求职意向配置模块
YAML配置分段（v0.7.0 已写入真实画像，`user_resume` 1185 字 / `user_intention` 562 字）：
```yaml
# 用户简历文本
user_resume: |
  粘贴简历全文（教育背景、项目经历、掌握技术栈等）
  # 当前实例：西安电子科技大学 211 · 数据科学与大数据技术 2027 届本科
  # 项目：购物商城（Spring Boot/Redis/RocketMQ）+ Android 环境监测 App

# 用户求职意向
user_intention: |
  意向岗位：后端开发工程师
  意向城市：西安、上海、成都、深圳（一视同仁）
  硬性排除：销售、客服、倒班、教培（命中应低于 30 分）
  偏好：小而美外企优先、WLB（双休/无强制加班/996/大小周）
  薪资底线：税前年薪（base+奖金）≥ 10 万
  技术栈口径：主栈 Java/Spring Boot/Spring Cloud/MySQL/Redis/RocketMQ；
    Python/Go/Kafka = 了解但无实战 → 岗位要求时扣分、作主要开发语言扣分；
    AI 辅助开发 / AI Agent 应用开发后端岗可接受，但核心语言须 Java 主栈为主
```
用户随时修改，修改后新的岗位打分基于最新简历与意向。程序不预先提取固定标签，直接把完整文本交给LLM。

## 4.4 AI岗位结构化抽取模块
输出字段：公司名称、岗位名称、工作地点、学历要求、技术栈要求、投递方式、截止时间、信息来源。
允许字段为空，缺失字段标记【信息未提及】。

## 4.5 岗位匹配打分模块
输入：结构化岗位信息 + user_resume + user_intention + **公司外部检索资料**（v0.7.0：多源搜索 + 牛客浏览器兜底的风评/WLB 资料）
由LLM完成对比：
1. 岗位要求与用户简历能力匹配度（**口径 v0.7.0**：主栈 Java/Spring Boot/Spring Cloud/MySQL/Redis/RocketMQ；Python/Go/Kafka 了解无实战——岗位要求时扣分、作主要语言扣分；AI 辅助开发/AI Agent 后端岗可接受但核心语言须 Java 主栈为主）
2. 岗位地点、岗位类型与用户求职意向匹配度（四城一视同仁；硬排命中即低于 30 分；外企/WLB 偏好加分不扣分；年薪底线 10 万，未注明不扣分投递前人工确认）
3. 公司外部核验：员工风评/WLB（牛客面经/评价/offer 投票等），只影响风险提示与偏好加分，不改变岗位本身匹配度
输出：0~100匹配分数 + 简短打分理由。
后置过滤逻辑：打分完成后读取配置`recommend_score_threshold`。分数≥阈值，标记为推荐岗位；分数＜阈值标记为仅存档岗位；**修改阈值自动全量重算全部已存档岗位（v0.7.0）**。
残缺岗位前置补全：缺公司名/岗位名的岗位先走浏览器补全链路（见 2.2 功能需求 10），补全成功才参与本模块打分。

## 4.6 本地数据归档与日报模块
目录结构（v0.7.0 更新）
```
./data
    /raw_msg            # 原始消息文本
    /image_raw          # 下载的图片原始素材（OCR 输入）
    /ocr_result         # 图片OCR识别结果
    /web_content        # 抓取网页正文
    /jobs               # 结构化岗位json
    /report             # Markdown日报
    /logs               # 运行日志（main.log / main_err.log / web.log / web_err.log）
    /jobs_dedup_backup_*    # 自动去重移动的重复岗位（保留最优、重复不删除）
    /jobs_deleted_backup_*  # Web 手动删除的岗位（投完归档、可恢复）
    /logs_archive_*         # 历史运行日志归档
```
日报内容：岗位按匹配分数降序排列，附带分数、打分理由、信息来源。

- 存储规则：所有识别到的岗位（无论分数高低），结构化 JSON 全部存入`./data/jobs`目录永久存档；岗位结构化 JSON 字段设计一次性定义完整，字段结构兼容后续 V2.0 Web UI 读取需求；后续新增 UI 模块时，可直接复用现有存储结构，无需修改底层存储格式。
- 去重规则（v0.7.0 增强）：按归一化公司+归一化岗位分组（别名表 + 去后缀 + 泛校招归并），保留最优（推荐优先 → 分数高 → 字段完整 → 文件新）；启动自动清理，重复移入 `jobs_dedup_backup_` 备份不删除。
- 阈值重算（v0.7.0）：修改 `recommend_score_threshold` 后（Web 保存/启动）全量重算推荐标记，`recommended = score >= threshold`，只改标记不改分数，幂等。
- 日报生成规则：Markdown 日报**只读取标记为推荐岗位（≥阈值）**，按匹配分数降序排列，附带分数、打分理由、信息来源。低分岗位不写入日报。
- 查看入口（v0.6.3 起 Web UI 落地，v0.7.0 增强）：Web 控制台（`http://127.0.0.1:8099`）岗位看板 / 日报预览 / 实时日志 / 状态与配置 + **手动录入 / 手动删除**；终端控制台实时输出 + 本地 Markdown 日报 + JSON 存档文件并行保留。

# 五、部署实施流程
## 5.1 环境准备
Windows本地电脑；部署NapCat；准备 DeepSeek 官方 API Key；安装PaddleOCR本地依赖；网页请求依赖库；**残缺补全/风评检索需安装 Playwright + Chromium**（`python -m playwright install chromium`，仅 anaconda Python 3.11 环境可用）。
## 5.2 NapCat部署配置
1. 本地部署NapCat，登录主力QQ。
2. 安全配置：禁用所有消息发送接口，纯只读模式。
3. 配置NapCat正向 WebSocket（OneBot v11）事件推送，供本程序订阅。
4. 开启 NapCat HTTP 服务（`onebot11_*.json` 的 `httpServers` 数组增加元素，**必须包含 `name` 唯一标识**，如 `"name":"http-backfill"`、`"host":"127.0.0.1"`、`"port":3002`）：供历史消息补拉（`get_group_msg_history` 扩展 API）使用；配置后重启 NapCat 生效。
## 5.3 LLM 服务（DeepSeek 官方 API 直连）配置
1. 注册 DeepSeek 开放平台（platform.deepseek.com），在「API Keys」页面创建 API Key（sk-...，按量计费）。
2. 编辑 yaml 配置文件（`job_assistant/config/config.yaml` 的 `llm` 段）：`llm.base_url` 指向 DeepSeek 官方 OpenAI 兼容地址 `https://api.deepseek.com/v1`，`llm.api_key` 填 DeepSeek 官方 API Key，`llm.model` 填模型名（如 `deepseek-chat`）。
3. 填写监听群ID列表、简历、求职意向；开启/关闭OCR、网页抓取。
4. **启动运行（v0.7.0 起）**：`powershell -File tools\scripts\start_all.ps1` 一键启动主程序 + Web 控制台（日志统一输出 `data/logs/`），`tools\scripts\stop_all.ps1` 停止；Web 控制台端口 8099（`http://127.0.0.1:8099`）。
## 5.4 测试流程
1. 单群测试：仅配置1个群ID，发送测试文本、招聘海报图片、招聘链接，验证消息捕获、OCR、网页抓取、岗位抽取、打分。
2. 多群测试：新增第二个群ID，验证仅监听配置内群，其他群消息被过滤。
3. 安全校验：确认程序不会发送任何消息。间歇启停验证。
- 新增测试场景 1：岗位打分等于阈值（当前配置 50 分），预期：完整信息在控制台输出，写入日报，JSON 存档。
- 新增测试场景 2：岗位打分 49 分，预期：仅 JSON 存档，控制台仅简短日志，不写入日报推荐列表。

# 六、风险分析与应对方案
1. **QQ账号风控风险**
    - 风险：NapCat协议读取消息、拉取图片资源，存在小概率触发人脸核验、账号限制风险。
    - 应对：只读模式、间歇启停、本地固定IP；出现人脸核验立即停止程序。
2. **网页抓取限制**
    - 风险：JS渲染页面、登录态页面无法获取内容；部分网站反爬限制IP。
    - 应对：增加超时与页面大小限制（4MB）；提供开关，不需要时关闭网页抓取；**残缺补全/风评检索链路支持 Playwright 无头浏览器渲染兜底**（v0.7.0），渲染失败降级不阻断。
3. **OCR识别误差**
    - 风险：海报字体模糊、倾斜，OCR识别错乱。
    - 应对：OCR识别失败标记异常；LLM容错解析，不强行补全信息。
4. **LLM解析误差**
    - 风险：宣讲文案格式不统一，部分字段抽取不全。
    - 应对：字段允许为空，日报标注信息缺失。
5. **平台登录墙（v0.7.0 新增）**
    - 风险：小红书搜索/笔记需登录态，无头浏览器与 HTTP 均被"手机号登录"拦截，员工风评覆盖不全。
    - 应对：保留小红书语境检索词（能命中索引摘要即纳入）；WLB 判断以牛客等可获取来源为主；如需要小红书完整内容，用户提供登录态后接入浏览器会话。
